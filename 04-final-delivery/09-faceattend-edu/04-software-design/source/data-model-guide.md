# Data Model Guide — FaceAttend-Edu

## 1. Overview

FaceAttend-Edu is an *attendance management platform based on biometric recognition* for educational institutions. The data model supports:

- Management of people, users, and credentials
- Academic structure (campuses, programs, periods, cohorts, courses, actors, and enrollments)
- Schedules and class sessions
- Attendance recording from multiple sources (facial, manual, IoT, import)
- Justifications with document support
- Biometric template updates with an approval workflow (`biometric_update_case` unifies FACIAL/FINGERPRINT)
- Biometric templates (facial and fingerprint) stored as *NoSQL collections in MongoDB*
- Alerts and notifications
- Academic and security configuration
- Quality evaluation of the microservices (ISO/IEC 25010, ISO/IEC 29110, ISTQB) — *Quality* context

Bounded Context	Tables / storage	Responsibility

AUTHORIZATION	4 tables	Administration of roles, permissions, and access assignments.
ACADEMIC	8 tables	Management of institutions, programs, academic periods, cohorts, courses, academic actors, and enrollments.
SCHEDULING	3 tables	Management of environments, schedule blocks, and class sessions.
ATTENDANCE	5 tables	Recording of attendance, justifications, supporting documents, and reports.

2.3. Relationship between users and people

In the IDENTITY context, the column app_user.person_id has a UNIQUE constraint, intended to establish a one-to-one relationship between app_user and person.

erDiagram
    PERSON o|--o| APP_USER : "person_id UNIQUE"

    PERSON {
        bigint id PK
    }

    APP_USER {
        bigint id PK
        bigint person_id FK, UK
    }


The one-to-one cardinality means that a person can be associated with a single user and that a user can be associated with a single person. To guarantee that every user has an associated person, person_id must also be NOT NULL; the foreign key must be defined to guarantee referential integrity.

2.4. Persistence and infrastructure considerations
Relational persistence: the IDENTITY, AUTHORIZATION, ACADEMIC, SCHEDULING, ATTENDANCE, CONFIGURATION, NOTIFICATION, and QUALITY contexts are represented as relational tables.
Document persistence: BIOMETRIC uses MongoDB to store the facial_emb and fingerprint_emb collections.
Physical location of QUALITY: although it is an independent bounded context from the domain perspective, its 7 tables are hosted in the quality schema of the 07-ms-configuration-db database.
Migration management: there is no separate quality-liquibase service; the QUALITY tables are physically located inside the database associated with CONFIGURATION.

Consequently, the model comprises 9 business bounded contexts, although QUALITY shares persistence infrastructure with CONFIGURATION. This physical location does not mean that both contexts should be considered a single bounded context from a conceptual point of view.

## 3. Context: Identity

*Responsibility:* Identity of people, access credentials, sessions, and password policies.

| Table | Description | PK |
|---|---|---|
| `person` | Base identity: document, name, contact | `person_id` (UUID) |
| `app_user` | Access credentials; 1:1 with `person` (`person_id` UNIQUE) | `user_id` (UUID) |
| `user_session` | Active/closed sessions | `session_id` (UUID) |
| `password_policy` | Password complexity rules | `policy_id` (INT) |

**Internal relationships (real FK):**
- `app_user.person_id` → `person.person_id`
- `user_session.user_id` → `app_user.user_id`

*Key design:* `person` *does not have* `school_id`. Identity is campus-agnostic.

> *Historical note:* the `city` table existed in this context but was *removed* (changeset `008-drop-city-table.yaml`). The geographic reference to a city is now resolved through an external catalog (countriesnow API), with no FK or dedicated table.

---

## 4. Context: Authorization

*Responsibility:* Role-based access control (RBAC).

| Table | Description | PK |
|---|---|---|
| `role` | Catalog of system roles | `role_id` (INT) |
| `permission` | Catalog of atomic permissions | `permission_id` (INT) |
| `role_permission` | N:N assignment of roles ↔ permissions | `(role_id, permission_id)` |
| `user_role` | N:N assignment of users ↔ roles | `(user_id, role_id)` |

**Cross-context (no FK):**
- `user_role.user_id` → `Identity.app_user.user_id`

*Key design:* `role` *does not have* `school_id`. Roles are global.

---

## 5. Context: Academic

*Responsibility:* Academic structure: campuses, programs, periods, cohorts, courses, actors, and enrollments.

| Table | Description | PK |
|---|---|---|
| `school` | Educational campus | `school_id` (INT) |
| `program` | Curricular offering of a campus | `program_id` (INT) |
| `academic_period` | Time window (quarter/semester) | `academic_period_id` (INT) |
| `cohort` | Group of students in a program + period | `cohort_id` (BIGINT) |
| `course` | Subject/course of a program | `course_id` (INT) |
| `academic_actor_type` | Catalog: STUDENT / INSTRUCTOR / ADMIN (campus administrator) | `actor_type_id` (SMALLINT) |
| `academic_actor` | Role that a person fulfills at a campus | `academic_actor_id` (BIGINT) |
| `enrollment` | Enrollment of an actor in a cohort | `enrollment_id` (BIGINT) |

**Internal relationships (real FK):**
school → program → course school → program → cohort ← academic_period academic_actor → academic_actor_type academic_actor → school enrollment → academic_actor enrollment → cohort


**Cross-context (no FK):**
- `academic_actor.person_id` → `Identity.person.person_id`

**Key differences:**
- *`program`*: Highest-level curricular container ("Technology in Data Analysis")
- *`course`*: Unit of content within a program ("Databases I")
- *`cohort`*: Specific group of students who progress together ("Cohort 2691234 — ADSI — Term 1 of 2026")

## 6. Context: Scheduling

*Responsibility:* Translates the academic structure into concrete schedules and sessions.

| Table | Description | PK |
|---|---|---|
| `environment` | Physical space (classroom, laboratory) | `environment_id` (INT) |
| `schedule_block` | Recurring weekly block | `schedule_block_id` (BIGINT) |
| `class_session` | Materialization on a specific date | `class_session_id` (BIGINT) |

**Cross-context (no FK):**
- `environment.school_id` → `Academic.school.school_id`
- `schedule_block.cohort_id` → `Academic.cohort.cohort_id`
- `schedule_block.course_id` → `Academic.course.course_id`
- `schedule_block.instructor_actor_id` → `Academic.academic_actor.academic_actor_id`
- `class_session.opened_by` / `class_session.closed_by` → `Academic.academic_actor.academic_actor_id`

**Business indexes (unique):**
- `(environment_id, day_of_week, starts_at)` → prevents double-booking the same environment.
- `(instructor_actor_id, day_of_week, starts_at)` → prevents double-assigning the same instructor.

*Bridge to Attendance:* `class_session` is the entity that receives attendance records.

## 7. Context: Attendance

*Responsibility:* Attendance recording, justifications, supporting documents, and reports.

| Table | Description | PK |
|---|---|---|
| `attendance_record` | One record per actor and session | `attendance_record_id` (BIGINT) |
| `justification_type` | Catalog of justification types | `justification_type_id` (INT) |
| `justification` | Justification for absence/tardiness | `justification_id` (BIGINT) |
| `supporting_document` | Attached supporting documents | `supporting_document_id` (BIGINT) |
| `attendance_report` | Generated attendance report (JSON snapshot) | `report_id` (UUID) |

**Internal relationships (real FK):**
- `justification.attendance_record_id` → `attendance_record.attendance_record_id`
- `justification.justification_type_id` → `justification_type.justification_type_id`
- `supporting_document.justification_id` → `justification.justification_id`

**Cross-context (no FK):**
- `attendance_record.class_session_id` → `Scheduling.class_session.class_session_id`
- `attendance_record.academic_actor_id` → `Academic.academic_actor.academic_actor_id`
- `justification.reviewed_by` → `Identity.app_user.user_id`
- `attendance_report.school_id` / `cohort_id` → `Academic`
- `attendance_report.generated_by` → `Identity.app_user.user_id`

*Business rule (unique index):* `(class_session_id, academic_actor_id)` is *unique* → only *one attendance record can exist per actor per class session*.

**ENUMs:**
- `attendance_status`: Present, Absent, Late, Justified
- `capture_method`: FACIAL, MANUAL, IOT, IMPORT
- `review_status`: Pending, Approved, Rejected

## 8. Context: Biometric

*Responsibility:* Biometric templates (facial and fingerprint).

*It is not part of the relational SQL schema.* It is modeled as NoSQL collections in *MongoDB* (outside the relational DBML model):

| Collection | Key fields |
|---|---|
| `facial_embedding` | `person_id`, `template_version`, `encoding`, `model_version`, `enrolled_at`, `is_active` |
| `fingerprint_embedding` | `person_id`, `finger_number`, `template_version`, `encoding`, `model_version`, `enrolled_at`, `is_active` |

*Why NoSQL?* Biometric embeddings are documents with a flexible structure and a high read/write volume due to real-time recognition.

*In PostgreSQL only the empty `biometric` schema exists* (`06-ms-biometric-db` only creates the schema, with no tables). The logical reference from `configuration.biometric_update_case.current_embedding_ref` points to the `_id` of the document in MongoDB (cross-paradigm, no FK).

---

## 9. Context: Configuration

*Responsibility:* Configurable parameters and biometric update cases.

| Table | Description | PK |
|---|---|---|
| `academic_configuration` | Parameters per campus | `configuration_id` (INT) |
| `security_configuration` | Global security parameters | `configuration_id` (INT) |
| `biometric_update_case` | Biometric update request | `case_id` (UUID) |

*`biometric_update_case`* unifies facial and fingerprint update cases:
- `biometric_type`: FACIAL / FINGERPRINT (ENUM)
- `finger_number`: Only for FINGERPRINT (1..10), null for FACIAL
- `current_embedding_ref`: Logical reference to the active document in NoSQL

## 9.5 Context: Quality

*Responsibility:* Quality evaluation instrument (ISO/IEC 25010, ISO/IEC 29110, ISTQB) applied to the other microservices. Logical owner: `09-ms-quality`; temporary physical hosting in the `quality` schema inside `07-ms-configuration-db`, because there is no separate `quality-liquibase` service — documented debt, do not move without a compatibilized migration.

| Table | Description | PK |
|---|---|---|
| `quality_project` | Evaluated software project (ISO/IEC 29110) | `project_id` (BIGINT) |
| `quality_evaluation` | ISO/IEC 25010 evaluation of a microservice | `evaluation_id` (BIGINT) |
| `quality_evaluation_item` | Score 1-5 per 25010 sub-characteristic | `evaluation_item_id` (BIGINT) |
| `process_assessment` | ISO/IEC 29110 process assessment (PM/SI) | `assessment_id` (BIGINT) |
| `process_assessment_rating` | N/P/L/F rating per 29110 objective | `process_rating_id` (BIGINT) |
| `istqb_assessment` | ISTQB CTFL v4.0 evaluation of a microservice | `istqb_assessment_id` (BIGINT) |
| `istqb_assessment_item` | Score 1-5 per ISTQB item | `istqb_assessment_item_id` (BIGINT) |

**Internal relationships (real FK):**
- `quality_evaluation.project_id` → `quality_project.project_id`
- `quality_evaluation_item.evaluation_id` → `quality_evaluation.evaluation_id`
- `process_assessment.project_id` → `quality_project.project_id`
- `process_assessment_rating.assessment_id` → `process_assessment.assessment_id`
- `istqb_assessment.project_id` → `quality_project.project_id`
- `istqb_assessment_item.istqb_assessment_id` → `istqb_assessment.istqb_assessment_id`

The catalogs of sub-characteristics/objectives/items (e.g. `tech-bva`, `PM.O1`) live in code (`09-ms-quality/src/domain/{iso25010,iso29110,istqb}.ts`), not in tables: the instrument is immutable, so they carry no FK.

## 11. Most important rule: No FKs between contexts

> **Every reference between different contexts is documented as a comment, never as an active `Ref:`.**

This means that in the SQL/Liquibase code:

```yaml
# CORRECT - no real FK
- column:
    name: person_id
    type: UUID
    remarks: "Cross-context reference to Identity.person (NO FK)"

# INCORRECT - real FK between contexts
- addForeignKeyConstraint:
    baseColumnNames: person_id
    referencedTableName: person
    referencedTableSchemaName: identity
Exception: References within the same context DO use real FKs (e.g. enrollment.cohort_id → cohort.cohort_id, both in Academic).
```

## 14. Auditing and cross-cutting best practices

Every table in the model includes a standard block for auditing and concurrency control.

### 14.1. Audit fields

```yaml
Column	Type	Purpose
created_at	datetime	Record creation date.
updated_at	datetime	Date of the last modification.
deleted_at	datetime (nullable)	Soft delete: NULL indicates the row is active.
created_by	UUID	User who created the record.
updated_by	UUID	User who modified the record.
deleted_by	UUID	User who logically deleted the record.
row_version	BIGINT (default 1)	Optimistic concurrency control (optimistic locking).
```

### 14.2. Associated rules
*Soft delete:* the value deleted_at IS NULL identifies active rows.
Partial unique indexes: unique indexes sensitive to soft delete use WHERE deleted_at IS NULL clauses; for example, uq_person_email.
*ENUM types:* they are created as native PostgreSQL types during the 01-ddl/02-types/ phase of Liquibase.
*Referential integrity:* real foreign keys are used only within each context, according to the rule described in section 11.

## 15. Physical layer (implementation)
### 15.1. Database topology

*PostgreSQL*

*Database:* faceattend_db.
Development: one database with eight main schemas (identity, authorization, academic, scheduling, attendance, biometric, configuration, and notification), plus the quality schema, hosted in the same database.
Production: serverless PostgreSQL on Neon. For more details, see DESPLIEGUE.md and database/docker-compose.neon.yml.

### 15.3. Liquibase migration cycle

Each domain runs its changes in the following order:

01-ddl → 02-dml → 03-dcl → 04-tcl


The phases have the following responsibilities:

```yaml
Phase	Responsibility
01-ddl	Creation of schemas, types, tables, and triggers.
02-dml	Insertion of initial data (seeds).
03-dcl	Configuration of roles and permissions (GRANT).
04-tcl	Functions and triggers implemented in PL/pgSQL.
```

Structure per domain:

```yaml
changelog/changelog-master.yaml: master migrations file.
01-ddl/: data definition changes, organized in subdirectories (01-schemas to 08-triggers).
02-dml/: initial data with context: seed.
03-dcl/: access control and permissions.
04-tcl/: functions and transactional logic.
05-rollbacks/: currently empty; contains databaseChangeLog: [].
```

Liquibase image version: liquibase/liquibase: 4.29.0.

### 15.4. Documented physical debts and limitations

Quality without its own Liquibase service: the Quality context is temporarily hosted in the quality schema of 07-ms-configuration-db. 
It must not be moved without a compatibilized migration.

Removal of city: the geographic reference school.city_id points to an external catalog (countriesnow API), 
with no dedicated table or local foreign key.

Reference between SQL and MongoDB: biometric_update_case.current_embedding_ref points to the _id of a MongoDB document.
Since it is a reference across persistence paradigms, there is no physical referential integrity between the two systems.
